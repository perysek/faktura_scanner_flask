## Problem Statement

A beauty salon owner in Poland manages supplier invoices through a chaotic manual workflow: paper invoices are photographed on a smartphone and passed to an external accountant, PDF invoices received via email are forwarded or lost in spam, and payment tracking does not exist ... payments are driven by collection department reminders. The accountant operates in permanent firefighting mode.

As of April 1, 2026, Poland's mandatory KSeF (Krajowy System e-Faktur) e-invoicing system requires ALL VAT-registered businesses to process B2B invoices electronically. Since February 1, 2026, all businesses must be capable of receiving invoices via KSeF. Invoices issued through KSeF are legally considered delivered even if the recipient never checks. Penalties up to 100% of VAT amount apply from January 2027.

The salon already has a fully functional invoice management app (MyWay Nails & Beauty) with OCR scanning, email inbox integration, payment tracking, dashboard, and alerts. The only gap is KSeF API integration.

## Demand Evidence

- The salon owner's current workflow involves zero payment tracking ... she discovers overdue invoices only when collection departments send reminders
- Paper invoices are photographed and forwarded to an external accountant; PDF invoices are lost in email spam
- The external accounting service is in "firefighting" mode, reactively handling disorganized invoices
- KSeF mandate (Apr 1, 2026) has transformed this from a convenience problem to a compliance obligation with financial penalties

## Status Quo

- Paper invoices: photographed on smartphone, sent to external accountant
- PDF invoices: received via email, forwarded to accountant or lost in spam
- Payment tracking: non-existent; driven by collection department reminders
- Accountant: external service provider in permanent firefighting mode
- No visibility into what's owed, when it's due, or what's overdue

## Target User & Narrowest Wedge

**Target user:** The salon owner (Piotr's wife) ... a small business owner who manages supplier relationships, pays bills, and runs the business. She is not technical. She needs invoices organized and payments tracked without learning XML or government portals.

**Narrowest wedge:** KSeF API integration into the existing MyWay app. The app already handles OCR scanning, email integration, payment tracking, dashboard, and alerts. KSeF becomes a new invoice data source alongside the existing ones. This is NOT a new product ... it's one integration that closes the compliance gap and adds automatic invoice ingestion.

**Key insight:** Small beauty salons primarily RECEIVE invoices from suppliers (cosmetics, equipment, rent). They rarely issue invoices. KSeF integration for this user means pulling received invoices, not publishing them.

## Constraints

- Flask + Jinja2 + Tailwind ... no framework changes
- Single-tenant for now (multi-tenancy deferred until market validation)
- Vanilla JS, no npm build steps for logic
- Must integrate with existing Invoice model (key fields include: seller_name, seller_nip, invoice_number, invoice_date, amount, currency, payment_due_date, payment_term, status, pdf_path, ocr_confidence, is_duplicate, among others)
- KSeF API authentication uses qualified electronic seals/tokens ... auth flow is reportedly complex (see Phase 0 below)
- Existing OCR and email pipelines must continue working alongside KSeF
- FA(3) = Faktura (version 3), the XML schema defined by the Ministry of Finance for structured e-invoices in KSeF

## Premises

1. The core product is a KSeF-powered invoice management dashboard for small service businesses in Poland, with OCR as a fallback for legacy paper invoices.
2. KSeF integration (pulling received invoices, payment tracking, accountant sharing) is now the PRIMARY value. OCR scanning is secondary.
3. Wife's salon is the test case. The broader market is every small Polish service business that needs a simple KSeF interface.
4. Salon management features (appointments, clients, employees) are a VERTICAL ADD-ON for beauty businesses, built on top of the horizontal KSeF invoice tool.
5. Ship single-tenant KSeF for the wife's salon first. Multi-tenancy is a scaling decision, not a launch decision.

## Recommended Approach

**Approach B: Full Invoice Lifecycle Integration.** The existing app already has OCR scanning, email integration, payment tracking, dashboard, and alerts. KSeF integration slots in as a new data source.

### Phase 0: KSeF Auth Discovery (PREREQUISITE — before any code)

Register the salon for KSeF access. Determine which auth flow applies:
- **Option A:** Qualified electronic seal (podpis kwalifikowany) — requires smart card or cloud signing service
- **Option B:** Authorized person token via the MF portal — simpler but requires portal registration
- **Option C:** ZAW-FA delegation to the accountant — paper form with turnaround time

Pull one real invoice manually through the KSeF web portal to validate access and capture the raw XML structure. **The entire effort estimate is contingent on this step resolving in under 2 days.** If auth requires HSM integration or ZAW-FA paper processing, the timeline extends significantly.

### Implementation Phases

1. **KSeF API client module** ... authenticate (token storage encrypted at rest, refresh/renewal flow, expiry handling), pull received invoices via `/online/Query/Invoice/Sync`, parse FA(3) XML with `lxml`
2. **Schema additions via Alembic migration** ... new fields on `invoices` table:
   - `ksef_reference_number` (TEXT, UNIQUE, nullable) — KSeF's canonical invoice ID
   - `source` (TEXT, default `'manual'`) — enum: `ocr`, `email`, `ksef`, `manual`. Backfill strategy for existing rows: rows with `ocr_confidence IS NOT NULL` → `'ocr'`; rows with a matching `upload_staging` record where `email_sender IS NOT NULL` → `'email'`; all remaining rows → `'manual'`. Note: perfect historical attribution is best-effort; some email-imported invoices that went through OCR may be marked `'ocr'` instead of `'email'`
   - `raw_xml` — stored in a separate table `ksef_invoice_xml` with `invoice_id` FK, NOT on the `Invoice` model itself. This avoids loading multi-KB XML blobs into memory for list views, dashboard stats, and search results. Fetched explicitly only in export routes and individual invoice detail views. Consistent with the existing pattern where `pdf_path` is a reference, not embedded content
3. **Invoice ingestion service** with two deduplication strategies:
   - **KSeF-to-KSeF:** deduplicate on `ksef_reference_number` as unique key (idempotent re-ingestion, skip if already exists)
   - **Cross-source matching:** when a KSeF invoice matches an existing OCR/email invoice by `invoice_number + seller_nip`, UPDATE the existing row (not INSERT) to add `ksef_reference_number`, `raw_xml`, and update `source` to `'ksef'`. This avoids conflicts with the existing partial unique index on `invoice_number WHERE is_deleted = FALSE`. Note: that index is global (not per-seller), which may need to become `(invoice_number, seller_nip) WHERE is_deleted = FALSE` once KSeF brings invoices from many suppliers.
   - **Merge field priority table:**

     | Field | KSeF wins? | Preserve existing? | Flag discrepancy? |
     |-------|-----------|-------------------|-------------------|
     | amount | Yes | No | Yes, if delta > 1% (log warning) |
     | invoice_date | Yes | No | Yes, if different |
     | payment_due_date | Yes | No | No |
     | seller_name | Yes | No | No |
     | seller_nip | Yes | No | No |
     | currency | Yes | No | Yes, if different |
     | bank_account | Yes | No | No |
     | pdf_path | No | Yes | No |
     | ocr_confidence | No | Yes (preserved for history) | No |
     | payment_term | Preserve existing | Yes | No (FA(3) may not have text payment_term) |
     | status | Preserve existing | Yes | No (user may have already marked as paid) |
4. **Scheduled sync via system cron** ... a standalone Python script (`scripts/ksef_sync.py`) invoked by system cron every 4-6 hours. NOT APScheduler in-process (unreliable with multi-worker deployments). The script authenticates, pulls, ingests, and exits. Flask reads results from the database.
   - **Error handling:** retry with exponential backoff (3 attempts, 1min/5min/30min). Failed syncs logged to `ksef_sync_log` table. Dashboard shows "Last sync: {timestamp}" indicator with red warning if last sync failed or is >12 hours old.
5. **Dashboard integration** ... KSeF invoices appear in existing invoice list with source badge (KSeF/OCR/Email/Manual)
6. **Accountant export enhancement** ... include KSeF XML alongside existing PDF/CSV exports

This approach is the right scope because:
- 90% of the infrastructure is already built and battle-tested
- KSeF becomes "just another input" to an existing pipeline
- No architecture changes needed
- Wife gets compliance within days, not weeks (assuming Phase 0 resolves quickly)

## Open Questions

1. **KSeF authentication:** What token/seal type does the salon use? Self-employed (qualified seal) vs. authorized person vs. accountant delegation (ZAW-FA)? This determines the auth flow complexity.
2. **Sync frequency:** How often should KSeF be polled? Real-time is overkill; daily might miss urgent invoices. 4-6 hour interval seems right.
3. **Duplicate detection:** When an invoice arrives via both email (PDF) and KSeF (XML), how should deduplication work? Match on invoice_number + seller_nip?
4. **KSeF API sandbox:** Is a test environment available for development before going against production?
5. **Accountant integration:** Does the external accountant already use KSeF? If so, should the app simply ensure the salon owner has visibility, while the accountant pulls from KSeF directly?
