  ---
  Why Vercel Is a Hard Fit

  Blocker 1: System Binary Dependencies (Fatal)

  pytesseract==0.3.13    # Requires Tesseract binary
  pdf2image==1.17.0      # Requires Poppler binary

  deployment package — Tesseract alone is 40MB+ and requires language data

  Blocker 2: Ephemeral Filesystem

  PDF_FOLDER.mkdir(parents=True, exist_ok=True)      # line 90

  Vercel serverless functions have no persistent filesystem. Only /tmp is
  writable, and it's cleared between invocations. Every uploaded PDF would
  vanish after the request ends.

  Blocker 3: SQLite on an Ephemeral Filesystem

  initialize_database()  # line 93 — creates an SQLite file

  The SQLite .db file lives on disk. On Vercel, this file does not persist 
  between requests — every cold start would recreate an empty database. You'd
  lose all invoices constantly.

  Blocker 4: Function Timeout

  Vercel free tier: 10-second timeout. Pro tier: 60 seconds. OCR on a multi-page
   Polish PDF (300 DPI rendering → Tesseract → regex) typically takes 15–60
  seconds per file. That's a hard runtime kill.

  Blocker 5: Cold Start Size

  Loading numpy, opencv, PIL, pytesseract on every cold start would take 5–15
  seconds before a single request is served.

● ★ Insight ─────────────────────────────────────
  This is a classic SQLite vs PostgreSQL batch_alter_table incompatibility.
  SQLite can't ALTER COLUMN directly, so Alembic's
  batch_alter_table(recreate='always') works around it by creating a new table,
  copying data, then dropping the old one — which fails in PostgreSQL because
  foreign keys on other tables reference services_pkey. PostgreSQL supports
  ALTER COLUMN natively, so the fix is to remove batch_alter_table entirely and
  use direct DDL operations. Since PostgreSQL uses transactional DDL, the failed
   migration was fully rolled back — the database is cleanly at the previous
  revision.
  ─────────────────────────────────────────────────

  The fix is straightforward — rewrite the migration to use PostgreSQL-native
  DDL:

● ★ Insight ─────────────────────────────────────
  SQLite has no native boolean type — it stores True/False as integers 1/0. When
   psycopg2 sends Python int(0) to a PostgreSQL BOOLEAN column, PostgreSQL
  refuses with a type error because it strictly distinguishes boolean from
  numeric types. The fix is a value coercion layer in the migration script:
  convert known integer values for boolean columns to Python bool before
  building the INSERT tuple. Python's bool(0) → False and bool(1) → True, which
  psycopg2 correctly maps to PostgreSQL FALSE/TRUE.
